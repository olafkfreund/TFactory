# Intent: api lane SUT/sidecar health failures must say why

## Problem

On factory-lab-cloud PR #1 (head 356fe6e) the generated-env nix Job ran, but the
SUT never accepted a connection on 127.0.0.1:8200 and all 7 api tests failed as
infra. The lane log keeps only `stdout[-300:]`; `/tmp/tf_app.log` (the SUT's own
traceback) is never printed, so neither the sidecar nor the SUT failure reason is
visible, and the Job is gone afterwards.

## Proposed outcome

- When the SUT is unhealthy, the Job prints the reason: the SUT process state and
  the tail of `/tmp/tf_app.log`; when a sidecar probe fails, which probe failed.
  The lane warning and lane stdout carry that block. Sidecar container logs are
  out of scope (the sandbox reads only the `lane` container; follow-up).
- The SUT readiness wait stops early when the SUT process has died, otherwise
  waits up to 60s, with each probe bounded (`--connect-timeout`/`--max-time`)
  and an HTTP 404 still counting as up.

## Affected users and systems

`agents/nix_env.py` (`_services_prelude`, serve prelude, unhealthy warning).

## Constraints

- No change to verdict classification (the marker stays the infra signal).
- The root cause for this repo cannot be read from a live Job (TTL expired); the
  change makes the next occurrence self-explaining and removes a too-short wait.

## Open questions

None. Decision (owner delegation): diagnostics first, no speculative env changes
to the generated flake.
