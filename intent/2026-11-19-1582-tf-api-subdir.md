# Intent: api lane resolves the python app nearest the spec targets

## Problem

aifactory-demo PR #624 (notes-api) on 0.13.3: all 10 generated api tests failed at import with
`No module named 'requests'` in the nix verify Job, and no SUT was served. The repo holds two
python apps: a link-shortener at `src/app` (root `pyproject.toml`) and the notes api in
`services/notes-api/` (own `requirements.txt`, `app/main.py`). Two root causes:

1. The repo commits a generated root `flake.nix` (fastapi, uvicorn, httpx, pytest, no `requests`).
   A repo-owned flake wins over the generated fallback, so the harness lacks `requests`.
2. Serve detection ignores the spec targets for python: it would boot the root `src/app` app
   (`uvicorn app.main:app`), not the notes api the spec names.

## Proposed outcome

For an api-lane spec whose targets live in a python subdirectory, the Job serves that
subdirectory's app (`uvicorn --app-dir <subdir> app.main:app`), and the env carries
pytest/requests/httpx even when the repo's committed flake is one TFactory generated.

## Affected users and systems

TFactory verify Job for the api lane (`agents/nix_env.py`, `agents/evaluator.py`).

## Constraints

- A hand-written repo flake is still respected; only a flake carrying the provisioner's
  GENERATED marker is regenerated, and only in the per-run scratch copy.
- Directory names reach a bash script: plain-name regex only (as #1609).
- No live cluster changes.

## Open questions

None. Decision (owner delegation 2026-11-19): regenerate marker-generated flakes in scratch
rather than editing the user's repo; least risky, reversible.
