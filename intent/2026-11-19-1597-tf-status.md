# Intent: task status endpoint must report spec-ingest progress (#1597)

## Problem

`GET /api/tasks/{id}/status` answers `is_running` only from `agent_service.running_tasks`, an in-process dict that spec-ingest tasks (planner and generator in-process, verify as k8s Jobs) never join. It also never sets `phase` or `message`. A running ingest task therefore shows `is_running:false, phase:null`. The MCP proxy calls the same function.

## Proposed outcome

For a task with a spec workspace, the endpoint reports `phase` and `message` from its `status.json`, and `is_running` is true while the persisted status is non-terminal, as well as when the in-process dict says so. A task with no workspace behaves as today.

## Affected users and systems

`routes/execution.py::get_task_status`, MCP `tasks/{id}/status`, cockpit pollers.

## Constraints

- Read-only; no new store. Reuse the spec-workspace layout `<root>/workspaces/<project>/specs/<spec>/status.json`.
- Workspace contents are read only after the project-level task authorization (`require_task_access("viewer")`) passes, and only for the `project:spec` id form; a bare id behaves as today.
- Path components validated with `safe_component`.

## Open questions

None. Decision (owner delegation 2026-11-19): use status.json (the issue's fallback) rather than a Postgres job-row lookup, because status.json carries phase and message and covers inline stages that have no job row.
