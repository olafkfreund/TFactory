# Spec: Fail closed when completed subtasks match no evaluator lane

## Design

In `run_evaluator` (apps/backend/agents/evaluator.py, step "2. No work"), when
`completed` is empty, first look for subtasks that are `completed` with
`files_to_create` regardless of lane (`_filter_completed_subtasks(plan, lambda st: True)`).
If any exist, write `status=evaluator_failed`,
`phase=evaluator_<mode>_no_lane_for_completed_subtasks`, and `evaluator_error`
listing the distinct (language, framework, lane) tuples, and return False.
Otherwise keep `_write_empty_verdicts`. It also deletes any stale `findings/verdicts.json` so the pipeline's unconditional
triage cannot consume a previous run's verdicts (Codex review finding); triage then
ends `triager_failed`, which `verify_pipeline` already treats as failed, like the
existing unsupported-language branch. The in-pod scheduler already notifies on
`evaluator_failed`.

Root cause of the reported run: stale server checkout without the Java lane;
`dev` already runs Java through the Maven nix lane (#1321, #1356). Reported as
an owner action (update the checkout the MCP server runs from), not code.

## Alternatives rejected

- New copy-into-module Java runner: the lane already exists and passes tests.
- Marking the task `stuck`: `evaluator_failed` is the existing terminal for an
  evaluator that cannot do its job and is already surfaced by Job reconcile.

## Risks

A plan with completed subtasks for a language that has a later-added lane but
whose plan carries an unexpected language string now fails loudly instead of
silently; that is the intent. Integration and mutation subtasks match no evaluator filter, so a plan holding only
those now fails loudly; that is honest missing coverage. Mixed plans are unchanged
(narrow scope: none admitted). Existing tests asserting `evaluated_empty` on such
plans must be updated.
