# Spec: widen the api fallback env to served python apps

## Design

`api_services_fallback_env` returns the fallback env when the lane is api and either services are required (today) or `detect_serve_command` finds a `uvicorn` command. The fallback env gains `verify_commands: ["python -m uvicorn"]` so `_python_libs` adds fastapi, uvicorn and httpx next to the always-present pytest, pytest-cov and requests; the SUT's own deps still come from its requirements/pyproject.

Known limit (Codex finding): deps only in pyproject.toml and unmapped are dropped by `_deps_from_pyproject`, and the Job pip-installs only requirements files. Out of scope; that failure surfaces as the existing SUT-boot-failed marker.

## Alternatives rejected

Adding libs to the host runner: it has no sidecar/SUT support, so tests still cannot reach a server. Routing every api repo to nix: node apps would get a python env they do not need.

## Risks

A python api repo that previously ran (and mostly failed) on the host runner now runs a nix Job, slower on a cold store. A uvicorn detection false positive costs one Job.

## Verification

Tests with a notes-api layout (`main.py` or `app/main.py`, no services): fallback is selected for api, not for unit, the Job script serves the SUT, and the generated flake contains requests and fastapi.
