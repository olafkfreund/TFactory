# Spec: probe reports "finished" only on evidence

## Design

In `_probe_job` (apps/backend/agents/verify_dispatch.py, tail), replace `active = bool(status.active)` with: `succeeded = (status.succeeded or 0) > 0 or a condition type Complete with status "True"`; `failed = a condition type Failed with status "True"`; `active = not (succeeded or failed)`. `status`, `succeeded` and `conditions` may each be None and read as absent; conditions with status "False"/"Unknown" do not count. `succeeded > 0` keeps its existing meaning (verify Jobs are single-completion, so one succeeded pod is the whole Job); `failed > 0` alone is never terminal because failed pods can be retried. Return `(True, active, succeeded)`. A Job with unset `active` (pod not yet scheduled or counted) is active, so `reap_if_orphaned` returns early on `job_exists and job_active`. A Job that really hit its deadline or backoff limit carries a Failed condition and is still reaped with the #464 reason. `liveness_sweep.job_active_probe` shares the probe and gets the same correction.

## Alternatives rejected

- Grace period after dispatch in `reap_if_orphaned`: needs a dispatch timestamp and still races slow schedulers.
- Count `status.ready`/`status.starting` as active too: still wrong for a pod that is pending; the terminal-evidence rule covers all of them.
- Rewriting #774 startup reconcile: no live trigger was found (see intent), so no speculative change.

## Risks

A Job deleted-and-recreated by hand keeps reading active until it has a terminal condition; its Job `activeDeadlineSeconds` (3600) bounds it. A Job with a Failed condition missing (older API) would stay active until GC returns 404, which the existing branch reaps.
