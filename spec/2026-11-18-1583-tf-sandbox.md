# Spec: fail closed on zero executed tests, services gate

## Design

1. `agents/confidence.py::enrich_verdicts`: stamp `signals_summary.failure_kind` from the classifier (already computed per test). New `apply_harness_import_override`: when `failure_kind == "import"` and `failure_detail` names a harness library (`requests`, `httpx`, `pytest`, `pytest_cov`, `coverage`, `yaml`... a small constant set), set verdict `not_run` with a system reason (infra, not an acceptance failure). Subject-module imports are untouched.
2. `agents/val_block.py::build_verification_block`: a verdict whose `signals_summary.failure_kind == "import"` never executed, so it counts as `not_run` for VAL-0/1/2 grading (a bare `flag` from an unexecuted test no longer proves a level). When there are no executed verdicts, the block gets `verdict_class`: `evaluated_empty` (no verdicts) or `infra` (verdicts exist, none executed) and the claim says so. When something executed, no `verdict_class` key is added.
3. `docker/tfactory-runner-pytest/Dockerfile`: add `requests==2.32.*` (the descriptor tells the generator it is installed).
4. `tfactory_yml/schema.py`: `services: list[ServiceSpec]` (`name` in postgres|redis, optional `version`), default empty. `agents/services_gate.py::declared_services(spec_dir)` reads the snapshot via `evaluator_targets._load_tfactory_cfg`. `gen_functional` calls it right after the plan loads, before any LLM spend: if any service is declared it writes `status=generated_empty`, `verify_skip_reason="unverifiable: needs services (postgres, redis): the verify sandbox cannot provision them (#1582)"`, `verdict_class="infra"`, and returns True. The existing #1253 zero-test envelope renders it as `empty` with that reason.

### Codex review corrections (2026-11-18)

- Services gate is ONE helper `agents/services_gate.py::halt_if_services_declared(spec_dir, project_dir)`, called at the start of the planner, of `run_gen_functional` and of `run_evaluator`, so no entry point (e.g. `planner._advance_to_evaluator`) bypasses it. It parses the real checkout (`load_tfactory_yml(project_dir)`) first, then the snapshot; an unreadable config is treated as "no services" and logged (the lane cannot know what it cannot read).
- Guarantee is stated for CLASSIFIED import failures (`failure_kind` stamped by the evaluator for every bundle). A collection error the classifier labels `unknown` is not covered; documented limitation.
- Harness-lib override is name-based: a subject that itself depends on `requests` and omits it would be misread as infra. Accepted and documented; the reason text names the module so the human sees it.
- The infra claim is written AFTER `normalize_verification` (which overwrites `claim`), and unexecuted verdicts are excluded from flag qualification (`_qualify_claim_with_flags`).
- A genuine VAL-3 disposable-target run (`val3.ran and passed`) is independent evidence and stays an exception to the VAL-0 ceiling; tested.

## Alternatives rejected

- Mark every import-failing verdict `not_run` including subject modules: would hide real defects from the coder and inflate accept rate (the #892 argument).
- Sidecar provisioning now: needs Job/pod spec and network-policy work and live validation; the owner's recommendation allows the explicit verdict first.
- testcontainers: optional per the owner, needs docker-in-sandbox.
- Collect-only preflight before generation: separate follow-up; the services gate covers the biggest cost leak (#1582).

## Risks

`not_run` verdicts leave accept-rate maths; mitigated because the VAL block now reports infra explicitly and the harness-lib set is narrow. A project that declares `services:` is now refused rather than attempted (intended). Runner image needs a rebuild/release to carry `requests`.
