# Spec: status endpoint reads status.json

## Design

In `get_task_status` (apps/web-server/server/routes/execution.py): for a `project:spec` id, add a route dependency that runs `require_task_access("viewer")` when the id contains `:` (a bare id skips it and keeps today's behaviour; shadow vs enforce mode is the platform's existing RBAC setting, not changed here), then read `<workspace_root>/workspaces/<project>/specs/<spec>/status.json` (root from `TFACTORY_WORKSPACE_ROOT` or `~/.tfactory`, components via `safe_component`). Set `phase` from the file's `phase`, `message` from `failed_reason`, else `reaped_reason`, else None, and `is_running = in_process or file status in ACTIVE_STATUSES`, the watchdog's own set of running statuses (`agents.liveness`). Missing, malformed or unknown-status files: `is_running` falls back to the in-process answer; phase/message still come from a readable file. The MCP proxy calls `get_task_status` after its own key and project authorization, and the proxied call passes only `task_id`, so the dependency lives on the HTTP route, not in the function. The MCP proxy calls the same function, so it is fixed too.

## Alternatives rejected

- Postgres job-row lookup (issue's first suggestion): rows exist only for Job-backed stages; planner/generator stages have none and phase/message are not stored there.
- Registering ingest tasks in `running_tasks`: per-pod, not durable, wrong across replicas.

## Risks

A status in the active set left behind by a dead control plane reads running until the #774 reconcile or liveness sweep fails it; that is the same truth `status.json` shows everywhere else.

tests/test_task_status_ingest.py (web-server): workspace tree under tmp, status `generating` + phase gives `is_running` true and phase set; `triaged` gives false; missing, malformed and unknown-status files give today's answer; a denied caller (enforce mode) gets no workspace data; traversal in the spec part is rejected.
